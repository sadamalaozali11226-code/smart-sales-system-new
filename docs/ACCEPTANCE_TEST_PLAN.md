# خطة اختبار القبول قبل البيع

آخر مراجعة: 2026-10-10  
الحالة: جاهزة للتنفيذ بعد توفير بيئة اختبار معزولة. **لم تُنفذ هذه الخطة على قاعدة الإنتاج.**

## بوابة السلامة قبل بدء الاختبارات

- [ ] تأكيد مشروع Supabase مستقل عن الإنتاج، والتحقق من معرّف المشروع واسم البيئة قبل إدخال أي بيانات.
- [ ] التأكد من أن Vercel Preview/اختبار يستخدم مفاتيح Supabase الخاصة ببيئة الاختبار، لا مفاتيح الإنتاج.
- [ ] إنشاء حسابات اختبار فقط، دون نسخ بيانات العملاء أو بيانات الإنتاج.
- [ ] توثيق baseline للمخزون والأرصدة قبل كل سيناريو، ثم حفظ النتائج ومعرّفات السجلات.
- [ ] عدم تفعيل الاختبارات إذا تعذر إثبات عزل قاعدة البيانات أو البريد الإلكتروني عن المستخدمين الحقيقيين.

## سيناريوهات القبول

| المعرّف | السيناريو | النتيجة المطلوبة |
|---|---|---|
| AUTH-01 | تسجيل حساب وتأكيد البريد | تصل الرسالة، ويُفعّل الحساب عبر الرابط الصحيح. |
| AUTH-02 | استعادة كلمة المرور | تصل رسالة الاستعادة، والرابط صالح لمرة الاستخدام المقصودة ولا يكشف بيانات حساب آخر. |
| ORG-01 | إنشاء مؤسسة وفرع وعضو | تنشأ السجلات المرتبطة بالمؤسسة الصحيحة فقط. |
| PERM-01 | عضو بلا فرع معيّن | لا تظهر له فروع غير مسندة ولا يستطيع قراءة بياناتها عبر واجهة أو RPC. |
| PERM-02 | عضو بلا صلاحية التقارير | تُرفض طلبات التقرير من الخادم، وليس بمجرد إخفاء عناصر الواجهة. |
| PERM-03 | تقارير فرع محدد | لا تتضمن مبيعات أو تكاليف فروع أخرى؛ تقرير المؤسسة يتطلب الصلاحية اللازمة. |
| INV-01 | إنشاء منتج وحركة مخزون | تتطابق الكمية الافتتاحية والحركات والكمية النهائية. |
| SALE-01 | بيع نقدي عادي | تُنشأ الفاتورة والحركة والمخزون مرة واحدة، وتطابق الإجماليات. |
| SALE-02 | بيع مع تحصيل جزئي | يطابق المدفوع والمبلغ المتبقي كشف حساب العميل. |
| SALE-03 | إعادة إرسال العملية أو الضغط المكرر | لا تنشأ فاتورة أو حركة مخزون مكررة. |
| RET-01 | مرتجع بيع جزئي | ينخفض صافي المبيعات بالمبلغ الصحيح، وتعود كمية وصافي تكلفة المرتجع للمخزون وفق سياسة النظام. |
| PUR-01 | فاتورة شراء | تزيد الكمية وتُسجل تكلفة الشراء في الفرع الصحيح. |
| PUR-02 | دفعة مورد وتخصيصها | مجموع التخصيصات لا يتجاوز الدفعة أو رصيد الفاتورة، ويطابق كشف المورد. |
| PUR-03 | مرتجع شراء | تنعكس الكمية والتكلفة ورصيد المورد على نحو صحيح دون تكرار. |
| EXP-01 | إنشاء مصروف بصلاحية صحيحة | يُنشأ المصروف مرة واحدة ويظهر في التقرير المناسب. |
| EXP-02 | إلغاء مصروف بصلاحية صحيحة | يُرفض الإلغاء دون الصلاحية المطلوبة، ويُسجل الإلغاء المسموح به مرة واحدة. |
| REPORT-01 | مطابقة تقرير المبيعات والأرباح | تطابق المجاميع فواتير الاختبار والمرتجعات والتكلفة والربح. |
| STORE-01 | تبديل المؤسسة أو الفرع | تتغير البيانات الظاهرة للسياق الصحيح؛ وعند الفشل يظهر إشعار واضح ولا يبقى سياق مضلل. |
| BACKUP-01 | استعادة نسخة احتياطية | تنجح الاستعادة في بيئة غير إنتاجية، وتطابق الجداول الأساسية والقيود والحركات بعد الاستعادة. |

## قواعد المطابقة المالية

- صافي المبيعات = المبيعات المؤهلة للتقرير − مرتجعات البيع، وفق سياسة الحالات المعتمدة.
- رصيد العميل = المبالغ المستحقة − المدفوعات والتسويات المسجلة؛ تحقق من إشارة كل نوع حركة وفق كشف الحساب.
- رصيد المورد = المشتريات − دفعات المورد − مرتجعات الشراء/التسويات، مع مراعاة طريقة عرض الرصيد المعتمدة.
- كمية المخزون النهائية = الرصيد الافتتاحي + الوارد − الصادر، مع فصل التحويلات والمرتجعات والإلغاءات حسب نوع الحركة.
- لا تُقبل فروقات غير مفسرة، أو كميات سالبة غير مسموح بها، أو حركات مالية مكررة.
- قارن الإجماليات على مستوى المستند ثم على مستوى التقرير؛ لا تعتمد على لقطة الشاشة وحدها.

## الأدلة المطلوبة لكل اختبار

1. معرّف بيئة الاختبار ووقت التنفيذ.
2. حساب الاختبار والدور والصلاحيات، دون حفظ كلمات المرور أو الأسرار.
3. خطوات التنفيذ والنتيجة المتوقعة والفعلية.
4. معرّفات المستندات وحركة المخزون/الدفعات ذات الصلة.
5. مقارنة قبل/بعد للمجاميع، ونتيجة PASS أو FAIL مع سبب واضح.
6. تنظيف بيانات الاختبار فقط بعد حفظ الأدلة، وبطريقة لا تتجاوز قيود سلامة السجلات المالية.

## شروط الإطلاق

لا يُعلن النظام جاهزًا بالكامل إلا بعد:
- اجتياز جميع السيناريوهات الحرجة، خصوصًا الصلاحيات وعزل المؤسسات والفروع والمخزون والمرتجعات والمدفوعات.
- التحقق من البريد الإلكتروني وإعادة تعيين كلمة المرور.
- إثبات قابلية الاستعادة.
- نشر النسخة المرشحة بعد نجاح CI، والتحقق من رابط الإنتاج والصفحات والأصول.
- إكمال سياسة الخصوصية وشروط الاستخدام والتسعير والدعم.
- تسجيل كل فشل وإصلاحه باختبار انحدار مناسب، وعدم إعادة اختبار مسار مستقر دون تغيير ذي صلة.

## الوضع الحالي

فحوص CI الحالية هي فحوص دخان HTTP وJavaScript وتدقيق تبعيات؛ وهي لا تعادل اختبار قبول متكاملًا للتدفقات المالية. آخر فحص للموارد أظهر مشروع Supabase واحدًا بلا فروع تطوير، لذا يجب أولًا توفير بيئة اختبار معزولة. لا تُجرَ عمليات اختبار على قاعدة الإنتاج ولا تُنشأ موارد قد تكون مدفوعة دون موافقة.
