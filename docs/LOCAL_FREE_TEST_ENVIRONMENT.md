# بيئة اختبار محلية مجانية — خطة آمنة

آخر مراجعة: 2026-10-10

## القرار

نبدأ بالخيار المجاني: بيئة محلية على جهاز المطوّر باستخدام Supabase CLI وDocker، مع قاعدة PostgreSQL محلية منفصلة عن مشروع الإنتاج. لا ننشئ مشروع Supabase جديدًا أو فرعًا مستضافًا، ولا نحتاج إلى ترقية مدفوعة لهذه الخطوة.

**هذه الوثيقة خطة تشغيل، وليست إثباتًا بأن البيئة المحلية شُغّلت أو أن اختبارات القبول نجحت.** يلزم جهاز تتوفر عليه Docker وموارد كافية؛ وقد تختلف إتاحة الأدوات بحسب نظام التشغيل.

## ما تأكد من المستودع

- يوجد `package.json` واختبار `npm test`؛ CI يستخدم Node.js 24 ويشغّل `npm ci --ignore-scripts` ثم `npm audit --omit=dev` و`npm test`.
- لم يُعثر على `supabase/config.toml` في جذر المستودع عند المراجعة.
- سجل ترحيلات الإنتاج لا يطابق ملفات الترحيل واحدًا بواحد؛ توجد 38 ملفًا في المستودع مقابل 56 سجلًا في قاعدة الإنتاج وفق آخر جرد. اختلاف الأسماء لا يثبت أن ترحيلًا مفقود أو لم يُطبّق.
- لذلك **لا تشغّل `supabase db reset` أو أي ترحيلات على الإنتاج، ولا تعتبر تشغيل كل ملفات المستودع إعادة بناء موثوقة لقاعدة الإنتاج** قبل إتمام مطابقة الترحيلات.

## خطوات البدء المجانية

1. على جهاز تطوير موثوق، ثبّت Node.js 24 وGit وDocker Desktop أو Docker Engine، ثم ثبّت Supabase CLI بالطريقة الرسمية المناسبة لنظام التشغيل.
2. استنسخ المستودع واعمل على نسخة محلية منفصلة:
   ```sh
   git clone https://github.com/sadamalaozali11226-code/smart-sales-system-new.git
   cd smart-sales-system-new
   git checkout main
   npm ci
   npm test
   ```
   هذه الخطوة تشغّل الاختبارات الموجودة فقط؛ لا تعتبر بديلًا عن اختبار قاعدة البيانات.
3. قبل تهيئة Supabase محليًا، راجع ملفات `supabase/migrations` ونتائج تقرير مطابقة الترحيلات. لا تستخدم أسرار الإنتاج ولا ملف `.env` الإنتاجي.
4. بعد تحديد مصدر موثوق لمخطط قاعدة الاختبار، أنشئ إعداد Supabase محليًا في نسخة العمل، ثم شغّل الخدمات المحلية فقط عبر CLI. تحقّق من عنوان قاعدة البيانات المحلية ومعرّف البيئة قبل تطبيق أي ترحيل أو إدخال بيانات.
5. أنشئ بيانات اصطناعية بالكامل (مؤسسة، فرع، مستخدمون، منتجات، عملاء وموردون تجريبيون). لا تنسخ بيانات العملاء أو المعاملات الحقيقية.
6. شغّل سيناريوهات `docs/ACCEPTANCE_TEST_PLAN.md` وسجّل النتائج الفعلية ومعرّفات سجلات الاختبار. لا تُسجّل PASS إلا عند التحقق من قاعدة البيانات والتقارير، لا من الواجهة وحدها.

## حاجز أمان إلزامي

قبل كل أمر يغيّر قاعدة بيانات، تأكد من أن عنوان الاتصال يشير إلى PostgreSQL المحلي. لا تستخدم مفاتيح الإنتاج، ولا تغيّر متغيرات Vercel/Supabase للإنتاج، ولا ترسل رسائل بريد حقيقية من بيئة الاختبار. استخدم مزوّد بريد محلي/وضع اختبار إن أمكن.

إذا لم يتوفر Docker أو لم يمكن إعادة بناء مخطط متسق من الملفات، نتوقف عند اختبارات `npm test` وفحوص القراءة فقط؛ لا نعوّض ذلك بتجارب على الإنتاج.
